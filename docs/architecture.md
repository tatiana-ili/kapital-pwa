# Архитектура «Капитал»

## 1. Анализ требований и границы первой итерации

Приложение — персональный mobile-first PWA для Android, который агрегирует выписки четырёх банков. Единственный доверенный способ получения банковских данных — ручной импорт файлов; прямые подключения, scraping, платёжные действия и хранение банковских учётных данных исключены.

Этап 1 включает Dashboard, экран Transactions, PWA-оболочку, светлую/тёмную темы, Supabase-клиент, PostgreSQL-схему с RLS и детерминированный demo dataset. Этап 2 реализует ручной импорт CSV, XLSX и текстовых PDF, сопоставление колонок, нормализацию, проверку дублей и атомарное подтверждение. Этап 3 добавляет каталог категорий, правила по продавцу и описанию, ручную смену категории и предложение сохранить правило. Аналитика, бюджеты, подписки, цели и AI остаются следующими итерациями.

## 3. SQL-модель

- `accounts` — счета и текущие остатки по банкам.
- `transactions` — единый ledger. `amount < 0` означает расход, `amount > 0` доход. `source_hash` уникален в пределах пользователя.
- `categories` и `category_rules` — системные/пользовательские категории и активные правила.
- `import_profiles` и `imports` — сохранённые mapping-профили и аудит файлов.
- `balance_snapshots` — история капитала.
- `budgets`, `goals`, `subscriptions` — таблицы следующих этапов, созданные заранее, чтобы не менять базовые связи.

Все персональные таблицы защищены Row Level Security правилом `user_id = auth.uid()`. Публичному браузерному клиенту разрешены только строки текущего пользователя. Service-role key не используется во frontend.

## 4. Архитектура импортёров (Этап 2)

```text
file → detector → bank parser → normalized rows → validation
     → fingerprint/dedup → transfer review → preview → atomic commit
```

Единый контракт парсера:

```ts
interface BankStatementParser {
  id: 'tbank' | 'sber' | 'yandex' | 'ozon';
  matches(fileName: string, preamble: string): boolean;
  inferMapping(headers: string[]): ColumnMapping;
  parse(options: ParseStatementOptions): StatementPreview;
}
```

Импортёр не пишет в БД во время чтения файла. Он возвращает одинаковые нормализованные строки и диагностические сообщения с номером строки. Если автоматическое сопоставление не подходит, пользователь получает preview колонок и mapping UI; mapping сохраняется в `import_profiles` по банку, формату и сигнатуре заголовков.

Банковские модули определяют источник по имени файла или заголовку перед таблицей и добавляют варианты названий колонок. Нормализация строк остаётся общей. При следующем импорте сопоставление загружается из `import_profiles` либо локального демохранилища и проверяется на допустимые индексы; неизвестный формат можно сопоставить вручную. Автоматическое распознавание проверено на обезличенных примерах CSV. Для подтверждения реальных версий выписок нужны отдельные fixture-файлы без персональных данных.

Fingerprint версии 2 строится из `bank + account name + transaction_date + amount + merchant + description`. Предпросмотр учитывает старые отпечатки версии 1 на том же счёте; PostgreSQL-триггер пропускает их при сохранении. Журнал повторного файла также ограничен счётом. Текст, похожий на перевод, и однозначная противоположная операция на другом счёте помечаются для проверки. После подтверждения перевода обе стороны связываются одним `transfer_group_id` и исключаются из аналитики. Неоднозначные совпадения остаются на ручной проверке.

PDF считается best-effort источником. Табличный PDF извлекается через PDF.js в браузере. Скан без текстового слоя отклоняется с рекомендацией использовать CSV или XLSX; OCR не выполняется.

После подтверждения RPC `commit_statement_import` одним вызовом создаёт или обновляет счёт, сохраняет mapping-профиль, журнал импорта, новые операции и снимок остатка. Функция работает как `security invoker`, поэтому RLS остаётся активным. Повторный `file_hash` и повторный `source_hash` не создают дубли.

## 5. Категории и правила (Этап 3)

Системный каталог совпадает с категориями ТЗ и читается всеми авторизованными пользователями. Свои категории и правила ограничены RLS. Операции хранят имя категории, поэтому пользовательское имя должно быть уникальным среди собственных и системных категорий независимо от направления. Если пользователь добавляет своё существующее имя для второго направления, категория становится общей для расходов и доходов. Переименование выполняется одной транзакцией PostgreSQL и обновляет операции, правила и бюджеты; деморежим делает то же в `localStorage`.

Правило содержит поле `all`, `merchant` или `description`, оператор `contains`, текст, направление операции, целевую категорию и флаг активности. Активные правила имеют приоритет над встроенной категоризацией, только когда направление и категория подходят знаку суммы. Новое или изменённое правило получает более высокий приоритет и сразу применяется к уже сохранённым операциям; внутренние переводы остаются исключением. Поиск в поле `all` не использует текущую категорию операции, чтобы результат повторного применения оставался стабильным. Команда проверки правил удаляет точные дубли, объединяет соседние условия по одной категории без изменения результата категоризации, повторно применяет правила ко всей истории и проверяет результат. При ревью под операцией показано подходящее активное правило, если оно есть. Если правила нет, при ручной смене категории приложение предлагает создать правило по имени продавца.

## 6. Планирование (Этап 5)

`/budget` хранит лимит для пары «категория + месяц». Расходы считаются по всем загруженным операциям выбранного месяца без внутренних переводов и строк, исключённых из аналитики. Переименование пользовательской категории обновляет и её бюджеты.

`/subscriptions` вычисляет кандидатов локально из нормализованных операций с отметкой регулярности либо категорией подписок, связи, коммунальных услуг, жилья или финансовых услуг: не менее трёх последних похожих оплат одного продавца, разброс суммы до 15% и одинаковые интервалы для недели, месяца, квартала или года. Более старые нерегулярные покупки не разрушают найденную последовательность. Это эвристика, поэтому кандидат можно уточнить или скрыть как ложное совпадение. Подтверждённые и отклонённые записи хранятся отдельно; отклонённая запись подавляет повторное предложение по тому же продавцу. Месячная сумма — среднее от годовой оценки.

`/goals` хранит название, целевую и текущую суммы и необязательную дату. Текущая сумма вводится пользователем вручную и не меняет банковские остатки. Ежемесячный взнос рассчитывается из оставшейся суммы и срока.

## 7. Глобальный поиск

`/search` использует полный набор нормализованных операций, загруженный через тот же пагинированный Supabase-запрос, что и аналитика. Поиск выполняется в браузере по продавцу, описанию, категории, заметке и точной абсолютной сумме; текст нечувствителен к регистру и различию `е`/`ё`. Несколько слов должны встретиться в одной операции, но могут находиться в разных полях. Банк показывается в каждой найденной строке, но его название не расширяет выдачу, чтобы запрос «Ozon» не захватывал все операции Ozon Банка. Результаты отображаются порциями по 40 строк, итоги рассчитываются по всей выборке и исключают внутренние переводы и скрытые из аналитики строки. Исходные файлы выписок не участвуют в поиске.

## 8. История капитала, наблюдения и настройки

Dashboard загружает `balance_snapshots` постранично и строит историю только по фактически сохранённым остаткам активных счетов. Для каждой даты последняя известная сумма по счёту переносится до следующего снимка; точки до первого снимка хотя бы одного активного счёта не показываются как общий капитал. В деморежиме используются отдельные синтетические снимки, а введённый при импорте остаток сохраняется локально. Наблюдения вычисляются из всей истории операций: внутренние переводы и скрытые строки исключаются, текущий неполный месяц сравнивается с таким же числом дней прошлого. Правки продавца и заметки не меняют `source_hash` и не нарушают защиту от повторного импорта. Тема — настройка устройства в `localStorage` и не смешивается с банковскими данными.

## 9. Основные риски и спорные места


1. Форматы банков меняются без версионирования. Нужны fixture-файлы без персональных данных и regression tests для каждой версии parser.
2. Банки по-разному показывают дату операции и дату проводки. Обе даты хранятся; fingerprint должен использовать стабильную выбранную дату и версию алгоритма.
3. Refund и card reversal легко принять за доход. Это отдельный `transaction_type`, а не категория дохода.
4. Внутренние переводы могут иметь комиссию, задержку и разные валюты. Auto-match должен иметь confidence и ручное подтверждение; комиссия остаётся расходом.
5. Остаток нельзя надёжно восстановить только по операциям, если выписка неполная. Источник истины для капитала — `accounts.current_balance` и `balance_snapshots`.
6. Demo-режим не является авторизованным production-режимом. После задания Supabase env приложение требует сессию; RLS остаётся обязательной последней линией защиты.
7. PWA-кеш хранит только статические ресурсы. Навигации, API-ответы и ответы внешнего Supabase origin исключены из кеша.
8. AI получает только минимальную выборку или агрегаты и не имеет мутационных банковских инструментов. Ключ должен оставаться только на сервере.
